# Session summary backfill

Hand-generates session summaries for sessions that have a real transcript but were
never run through `POST /api/summarize`, writing the same three tables the Worker's
`handlePostSummarize` writes.

Not part of the app. One-off catch-up tooling, kept because the same situation
(a batch of unprocessed sessions with transcripts) can recur.

## Why by hand

`POST /api/summarize` needs a Firebase staff ID token, which an agent session can't
mint. The endpoint is otherwise just "call Claude with a prompt, write 3 tables" —
so the summary is produced directly and written with the same contract.

## The contract (worker/index.js)

Two conceptual calls, merged into one object via `Object.assign`:

- **Review keys** (bilingual `{pt, en}` text blobs): `discussion_overview`,
  `recommendations`, `client_action_items`, `rafa_followups`, `next_session_focus`,
  `client_profile_updates`
- **pdf_data** (Portuguese ONLY — it is the client deliverable) + the 3 structured
  sections bilingual at top level: `business_diagnosis`, `swot_synthesis`,
  `thirty_day_goals`

Three writes:

| Table | Content |
|---|---|
| `sessions` | `summary_json`, `pdf_data`, `status='summarized'` |
| `session_summaries` | 20 columns — 6 text keys × pt/en, 3 structured × pt/en as JSON strings |
| `documents` | `pdf_data` verbatim |

### Fixed vocabularies — must match exactly

- `business_diagnosis`: exactly 10 rows, in this order, names in Portuguese in BOTH
  languages: `Produto/Serviço`, `Fundadores`, `Experiência do Cliente`,
  `Time Operacional`, `Time Comercial`, `Marketing & Presença Digital`,
  `Infraestrutura`, `Documentação Legal`, `Sistemas de Gestão`, `Parcerias`.
  Each row `{dimension, situation, level}`, `level` ∈ `FORTE|MÉDIO|FRACO|CRÍTICO`.
- `thirty_day_goals`: exactly 7 rows, in this order: `Operacional`, `Comercial`,
  `Marketing`, `Parcerias`, `Infraestrutura`, `Legal`, `Sistemas`.
  Each row `{area, meta, indicador}`.
- `thirty_day_plan`: exactly 4 weeks, `{week_label, week_title, items[]}`,
  each item `{text, owner}`, `owner` ∈ `CLIENTE|CONSULTOR` (uppercase).
- `document_title`: always the literal `"Relatorio\nEstrategico"`.
- Everything else: 2-4 items per array.
- `client_actions` / `consultant_followups`: `{text, due}` with `due` as
  `"DD Mon"` abbreviated Portuguese month, e.g. `"09 Jul"`.
- `headline_insights` `{title, body}`; `recommendations` `{number, title, body}`;
  `next_session_focus_points` `{number, text}`.
- `swot`: `{strengths[], weaknesses[], opportunities[], threats[]}`.
- `swot_synthesis`: `{forca_oportunidade, fraqueza_ameaca, forca_ameaca}`.

`active_sections` and `custom_sections` are stamped server-side, never by the model.
`build_sql.mjs` defaults `active_sections` to all 9 in canonical order.

## Usage

```bash
# 1. Write the summary JSON (see example-dfn-0708.json for the exact shape)
# 2. Generate SQL
node scripts/session-backfill/build_sql.mjs <session_id> summary.json > out.sql
# 3. Execute
npx wrangler d1 execute apex-command-center --remote --file=out.sql
```

Statements are too large for the D1 MCP query tool — use wrangler with `--file`.

## Verify after each write

```sql
SELECT s.status,
 json_array_length(json_extract(s.pdf_data,'$.active_sections')) AS n_active,
 json_array_length(json_extract(s.pdf_data,'$.business_diagnosis')) AS bd,
 json_array_length(json_extract(s.pdf_data,'$.thirty_day_goals')) AS tdg,
 json_array_length(json_extract(s.pdf_data,'$.thirty_day_plan')) AS tdp,
 (SELECT COUNT(*) FROM session_summaries x WHERE x.session_id=s.id) AS ss_rows,
 (SELECT d.pdf_data = s.pdf_data FROM documents d WHERE d.session_id=s.id) AS doc_ok
FROM sessions s WHERE s.id='<session_id>';
```

Expect: `summarized`, 9, 10, 7, 4, 1, 1.

## Gotchas found the hard way

- **`section_config` is not always NULL.** One session had 4 sections disabled.
  Nicole's call: generate all 9 and set `section_config = NULL` so Rafa decides
  in the UI what the PDF includes. Check it before writing.
- **Never read the PDF template file.** Token killer, and it is not the source of
  truth — the contract lives in `buildPdfPrompt()` in `worker/index.js`.
- **Approval does NOT generate tasks.** `handlePostApprove` only sets status,
  stamps `approved_at`, rebuilds `pdf_data`, upserts `documents`. Nothing in the
  Worker ever inserts session follow-ups into the `tasks` table.
- **The Fireflies id lives in `sessions.task_completions`** as
  `{"fireflies_id": "..."}`, not in `fireflies_transcript_id` (null everywhere).
  Do not clobber `task_completions` — it also holds Rafa's real task check-offs.
